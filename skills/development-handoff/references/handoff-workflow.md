# 产研交接操作流程

## 一、任务清单草稿

输入必须来自已经确认的需求范围、原型触点和用户指定的材料入口。AI 先建立三类任务草稿并执行需求、原型、接口和任务反查四项覆盖检查。

草稿允许存在覆盖缺口，但必须显式列出；不得为了通过检查自行补造业务规则、接口字段或非页面技术任务。

## 二、研发评审差异

研发评审结论按以下类型整理：

| 差异 | 处理方式 | 确认边界 |
|---|---|---|
| 新增 | 补入已有范围遗漏任务 | 研发确认，产品知悉 |
| 拆分 | 保留原业务目标，拆成可独立验收任务 | 研发确认 |
| 合并 | 合并不能独立验收的技术碎片 | 研发确认 |
| 删除 | 标记无需研发改动并记录理由 | 产品和研发核对范围 |
| 归类调整 | 在应用、接口或非页面任务间调整 | 研发确认 |
| 业务范围或验收变化 | 停止直接改清单，回到 CR | 产品与研发重新确认 |

AI 只整理差异，不代替研发或产品确认。

## 三、正式化

首次正式化前必须满足：

- 产品确认业务范围、非范围和验收结果；
- 研发确认任务拆分、研发端、接口和非页面任务；
- 不存在会改变实现结果的业务待确认问题；
- 四项覆盖检查通过；
- 材料入口可访问或已有明确人工确认。

实施环境、测试数据和接口联调条件可以作为实施前置条件保留，不因此改写业务范围。

## 四、为一个任务生成提示词

1. 用户明确指定一个正式任务编号；
2. 读取该任务和 `materialRefs`；
3. 逐项记录实际材料位置、获取时间和核对状态；
4. `matched` 记录实际版本；
5. `manual-confirmed` 记录确认人与日期；
6. `unverified` 保留警告，实施前必须人工确认；
7. `changed` 或 `missing` 停止生成并提出一个问题；
8. 使用确定性脚本生成提示词；
9. 明确报告“只生成，未实施”。

提示词只能包含当前任务关联材料。若发现另一个任务也需要相同能力，先登记范围问题，不自动扩大本次任务。

## 五、实施授权

“生成提示词”和“实施任务”是两次独立动作。

| 授权表达 | 当前允许 | 当前禁止 |
|---|---|---|
| 为 TASK-002 生成提示词，只生成不实施 | 读取任务关联材料、核对版本、生成提示词 | 修改代码、配置、数据、CR 和其他任务 |
| 开始实施 TASK-002 | 返回变更治理，核对授权范围和七项就绪检查 | 默认实施同一清单其他任务 |

正式任务清单可以支撑 `scope-clear` 和材料判断，但不替代 V0.3 七项就绪检查。实际实施必须由 `$change-and-delivery-governance` 控制。

## 六、钉钉与 Git 过渡期

- 只要求研发能够拿到材料，不限制必须通过哪个平台；
- 钉钉文档允许肉眼查看并人工确认；
- 已有合规 CLI 或工具时允许只读获取，但不在 Skill 中配置账号或凭证；
- Git 文件可记录提交或标签，但 Git 不是正式化的强制条件；
- 无法自动读取版本不等于材料失效，应标记 `unverified` 并把人工确认作为实施前置动作。

## 1. 这一批解决了什么

第三批把前两批确认的产品规则真正做成了可以运行的工具。

现在 Codex 可以根据产品经理确认的模式，创建一个干净的业务项目，并在后续迭代中帮助管理需求、风险、评审和交付。产品经理不需要直接操作终端、JSON 或底层治理文件。

一句话概括：**快速阶段不过度治理，进入持续迭代后再按需求风险补齐必要控制。**

## 2. 两种场景现在如何运作

| 场景 | 你提供什么 | Codex 做什么 | 你主要看到什么 |
|---|---|---|---|
| 客户现场或项目前期快速出 Demo | 有限的会议记录、验证目标和已知边界 | 推荐“快速验证”模式，得到你确认后创建项目并制作 Demo | 业务简报、可运行原型、评审确认单 |
| 需求评审后持续加功能 | 评审结论、继续建设范围和本次需求 | 切换到“持续迭代”，按风险安排分析、实施和评审活动 | 业务基线、需求状态卡、原型、检查结果 |
| 旧项目接入 | 旧项目和迁移授权 | 先给影响报告；不确定的内容集中问一次，确认后才迁移 | 迁移影响、待确认问题、迁移结果 |

AI 会推荐模式，但最终由产品经理确认。材料不清楚时，AI 只能继续梳理业务，不能擅自创建项目或进入实施。

快速项目另外使用一份 `validationProfile` 记录：本轮选择的评审目标、主要目标、AI 推荐理由、产品经理确认、输入充分度五项说明，以及是否启用独立评审中心。输入不充分时生成器直接阻断；输入部分充分或启用评审中心时，项目包含 Demo 蓝图。评审场景配置是原型运行数据，不是正式 CR 或业务规则。

## 3. 从快速验证切换到持续迭代

系统不会因为 Demo 做完、页面变多或项目运行时间变长而自动切换模式。

只有同时满足以下条件，才允许切换：

1. 需求评审结论为“通过”或“有条件通过”；
2. 已明确继续建设；
3. 产品经理确认切换；
4. 项目中有可追溯的评审记录；
5. 每条临时假设已标记为“已确认、已否定或仍待确认”。

切换后仍使用同一份业务基线，不会另建一套互相冲突的业务事实。

## 4. 持续迭代时，系统如何控制复杂度

每条需求先由 AI 建议风险等级，再由产品经理确认：

| 风险 | 适用理解 | 默认需要做什么 |
|---|---|---|
| 轻量 | 不改变核心规则的小调整 | 确认范围、实施、检查页面、产品评审 |
| 标准 | 常规功能或规则变化 | 分析影响、确认规则、维护触达页面、检查一致性、产品评审 |
| 高风险 | 涉及权限、资金、核心状态、外部系统、批量任务或不可逆操作 | 在标准活动上增加相应的决策、领域、异常或专项确认 |

产品经理日常看到的状态卡只有五项：

- 当前阶段；
- 当前结论；
- 为什么可以继续或为什么被阻断；
- 当前责任人；
- 下一步动作。

页面契约、领域模型和 B 端专项材料只有在需求实际触发时才创建，不会因为项目进入持续迭代就全部铺开。

## 5. 旧项目迁移和 Kit 升级是否安全

### 5.1 旧项目迁移

- 默认只生成影响报告，不修改项目；
- 找不到确定映射时停止，并把问题合并成一个待确认入口；
- 不改业务正文、原型行为和历史确认；
- 写入前先在临时副本验证；
- 写入前备份，支持恢复到迁移前；
- 未触达的旧模块保持“未审计”，不会被包装成已经治理完成。

如果旧需求已经走到待评审或完成，但缺少新规则要求的高风险证据，系统不会自动补成“已完成”，必须由产品经理确认已有证据或说明为何跳过。

### 5.2 Kit 升级

- 默认先预览会更新什么；
- 只更新 Kit 自己管理的运行文件和结构；
- 不覆盖业务基线、需求事实、决策和原型代码；
- 发现业务侧改过受管文件时停止；
- 升级前备份，支持恢复。

## 6. 交付给产品经理和发布 Kit 是两件事

- Kit 发布包包含模板、Skills、生成工具和内部说明，用于维护这套工具；
- 业务项目评审包只包含当前业务材料和可运行原型，不包含输入区、备份、依赖和 Kit 内部材料。

因此，把一个业务项目交给客户或评审人时，不会把整套 Kit 的内部操作材料一起带出去。

## 7. 请你评审这七个产品判断

- [x] 快速验证阶段只保留业务简报、原型和评审入口，材料足够精简；
- [x] 模式切换条件符合“需求评审后才进入持续迭代”的共识；
- [x] 轻量、标准、高风险三档处理深度合理；
- [x] 产品经理通过五项状态卡就能判断当前进展；
- [x] 条件性材料不会被过早创建；
- [x] 旧项目迁移和 Kit 升级的保护边界可以接受；
- [x] Kit 发布包与业务评审包的区分符合实际使用方式。

以上七项判断均已通过。第三批评审通过不自动授权第四批；第四批仍需明确说“开始第四批”。

## 8. 验证结论

- 两种模式的新项目均可创建并运行；
- 快速项目不会默认出现持续迭代材料；
- 标准和高风险需求会生成不同深度的活动；
- 未授权实施、无理由降级、缺少评审却宣布完成等 10 类问题会被阻断；
- 模式切换的预览、阻断和正式应用已验证；
- 旧项目迁移的预览、应用、歧义阻断、备份和恢复已验证；
- Kit 升级的预览、冲突保护、应用和恢复已验证；
- 全新快速项目已在独立目录完成依赖安装、检查、生产构建和评审包生成；
- 第三批当时的 Kit 完整检查、前端构建和 125 文件发布包校验通过；第四批回填后的最新发布结果以 `docs/review/v0.3-verification.md` 为准。

这些是工具级验证，不代表第四批的海马体和回收项目验证已经完成。

## 技术附录：产品评审时可跳过

### A. 固定名称

- 项目模式：`rapid-validation`、`continuous-iteration`；
- 需求阶段：`recorded、analysis-confirmation、implementation、awaiting-review、completed`；
- 风险等级：`light、standard、high`；
- 执行状态：`locked、ready、in-progress、waiting-human、paused、completed、cancelled`；
- AI 权限：`unassessed、planning-only、execution-allowed、human-only`。

需求总状态由阶段和执行状态自动得出，不在台账中重复维护。

### B. 关键实现边界

- `scripts/workflow-v3-lib.mjs`：需求阶段、风险活动、状态卡和完成门禁；
- `scripts/project-generator-lib.mjs`：两种业务项目的创建；
- `scripts/switch-project-mode.mjs`：快速验证切换持续迭代；
- `scripts/migrate-v02-to-v03.mjs`：V0.2 项目迁移；
- `scripts/upgrade-project.mjs`：Kit 版本升级；
- `scripts/business-runtime.mjs`：业务项目检查、视图生成和评审包生成。

标准或高风险需求实际触达页面并进入实施阶段后，才创建页面契约并生成页面说明。高风险页面根据权限、数据范围、外部系统、异常恢复等触发因素增加对应信息。

旧十一阶段迁移为五阶段；原证据、原台账和原影响 ID 保留在迁移记录中。V0.3 新增且无法由旧节点证明的高风险活动，通过 `risk-map.activityOverrides` 记录产品经理确认的完成证据或跳过理由。

### C. 原计划与验证证据

| 第三批要求 | 实现事实源 | 验证方式 |
|---|---|---|
| 五阶段、三级风险、暂停和派生状态 | 工作流核心 | 工作流校验、护栏测试 |
| 风险驱动活动 | 活动生成规则 | 高风险闭环及活动不匹配测试 |
| 简化状态卡 | 状态卡和可读视图生成 | 等待人工状态卡、视图同源检查 |
| 干净业务项目 | 项目生成器和模板清单 | 两种随机目录实例、独立构建 |
| 评审后模式切换 | 模式切换工具 | 空评审阻断、预览不写入、授权后切换 |
| V0.2 迁移和恢复 | 迁移工具 | 确定映射、高风险补齐、歧义阻断、摘要恢复 |
| Kit 升级和恢复 | 升级工具 | 新运行文件补入、业务摘要不变、冲突阻断 |
| 两类交付包 | 两类打包和校验逻辑 | Kit 发布包及业务评审包内容检查 |

完整自动检查命令为 `pnpm check`，Kit 生产发布检查为 `pnpm build:kit-release`。这些命令默认由 Codex 执行，不要求产品经理操作。

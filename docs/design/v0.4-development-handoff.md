## 1. 要解决的问题

V0.3 已经能够管理业务基线、CR、原型、页面契约、证据和评审，但需求评审结论到研发实际实施之间仍缺少一个稳定的交接视图：研发需要自行从完整需求和原型中识别本次到底要开发哪些应用端、菜单、接口和非页面能力。

V0.4 增加“产研交接”能力，将已确认需求拆成研发可以评审、理解和按任务调用编程 AI 的开发范围，同时保留以下边界：

- 需求仍然是业务事实源，研发任务不反向改写需求；
- 研发任务清单只定义开发范围，不承担负责人、工期和进度管理；
- AI 可以建议拆分和检查覆盖，但产品经理确认业务范围，研发确认技术拆分；
- 生成研发提示词不等于授权实施；
- Git、钉钉文档、原型地址和其他可访问材料都可以作为来源，不绑定单一平台。

## 2. 五个概念的关系

| 概念 | 回答的问题 | 是否为业务事实源 | 主要使用者 |
|---|---|---|---|
| 需求与 CR | 为什么做、做什么、业务结果和验收是什么 | 是 | 产品、业务、研发、测试 |
| 任务清单草稿 | AI 建议把已确认需求拆成哪些研发任务 | 否 | 产品、研发 |
| 正式研发任务清单 | 研发评审后，本次确认要开发哪些任务 | 是，限开发范围 | 产品、研发、测试 |
| 单任务研发提示词 | 编程 AI 执行某一个任务时需要哪些上下文 | 否，是按需生成视图 | 研发、编程 AI |
| 实施授权 | 当前是否允许修改代码或其他交付物 | 是 | 产品负责人或约定授权人 |

一条需求通常对应多个研发任务，例如同一个“订单审核”需求可能同时产生订单列表、审核弹窗、库存查询接口和失败重试任务。一个经研发确认的公共任务也可以关联多条需求。

每个研发任务都必须能回溯到已确认需求、研发评审结论或研发确认的技术必要项。任务清单不得成为无来源扩充业务范围的入口。

## 3. 在现有工作流中的位置

产研交接不新增 CR 主阶段，完整关系为：

`需求评审通过 → AI 生成任务清单草稿 → 研发评审 → AI 整理评审差异 → 产品与研发确认 → 正式研发任务清单 → 按任务生成研发提示词 → 单独授权实施`

其中：

- 需求评审确认业务方案和继续建设范围；
- 任务清单草稿在研发评审前生成，用于发现遗漏和不合理拆分；
- 研发评审确认应用端、菜单、接口、非页面任务和技术可实施性；
- 正式任务清单在研发评审后生成；
- 以上动作都发生在现有 `analysis-confirmation` 阶段内；
- 启用产研交接时，只有正式清单和现有就绪条件同时满足，且收到明确实施授权后，才进入 `implementation`。

纯原型评审或快速验证不强制创建研发任务清单。持续迭代项目只有在需要向真实研发实施交接时才启用，避免为不进入开发的需求增加材料负担。

## 4. 三方职责

### 4.1 AI

- 从已确认需求、原型和用户明确提供的评审材料中生成拆分建议；
- 将研发评审内容整理为新增、拆分、合并、删除和归类调整；
- 生成任务清单可读视图并执行覆盖检查；
- 按一个任务编号生成研发提示词；
- 遇到业务歧义、来源冲突或检测到评审后材料变化时停止并提问；
- 不自行确认业务规则、技术方案、正式清单或实施授权。

### 4.2 产品经理

- 确认任务清单覆盖了已经评审通过的业务范围；
- 确认明确非范围、业务规则和验收结果没有被研发任务改变；
- 区分业务范围变化与原范围内的技术任务遗漏；
- 首次正式化时完成产品侧确认。

### 4.3 研发负责人

- 确认任务能否实施以及拆分粒度是否合理；
- 确认涉及的前端、后端、数据、配置和其他研发端；
- 补充接口、公共能力、后台任务、初始化和异常保障等非页面任务；
- 首次正式化时完成研发侧确认。

AI 的覆盖检查只能证明已声明范围存在映射，不能证明所有潜在技术工作都已被发现。研发负责人的确认是“研发任务完整”结论不可替代的人工门禁。

## 5. 任务拆分原则

默认按“可独立开发和验收的业务能力”拆分，而不是机械地按一个页面一个任务，或把前端、后端、数据库分别拆成失去业务含义的碎片。

满足以下任一条件时可以继续拆分：

- 可以独立交付和验收；
- 依赖、风险或联调对象不同；
- 需要不同研发端独立承担且不会丢失业务目标；
- 研发评审明确要求拆分。

前后端共同完成一个业务结果时，默认保留为一个业务任务，并使用“涉及研发端”说明参与范围。只有研发确认存在独立交付边界时，才拆成多个任务。

“全部任务”只表示已确认交接范围内的全部任务，不表示 AI 能发现未被需求、原型或研发评审触达的所有技术工作。

## 6. 三类研发任务

### 6.1 应用功能任务

按照以下层级组织：

`应用端 → 一级菜单 → 二级菜单或页面 → 功能操作 → 研发任务`

核心信息包括任务编号、应用端、菜单或页面、功能操作、开发范围、涉及研发端、关联需求、验收要点、实施前置条件和关联材料。

### 6.2 外部系统接口任务

按照以下层级组织：

`外部系统 → 接口 → 对接方向 → 调用场景 → 研发任务`

核心信息包括系统方、接口名称、对接方向、调用场景、开发范围、关联需求、异常与验收、依赖或待确认条件和关联材料。

接口协议、字段、鉴权和技术方案只有在研发评审已经确认时才能写入正式任务。AI 不得为了填满表格自行设计。

### 6.3 非页面研发任务

用于承接没有直接菜单或页面入口，但属于确认开发范围的工作，例如：

- 定时同步和异步任务；
- 数据初始化或历史数据迁移；
- 后台服务与公共能力；
- 消息通知；
- 权限数据初始化；
- 日志、幂等、失败重试和审计能力；
- 接口鉴权配置。

非页面任务必须来自研发评审结论或明确需求，不得由产品经理或 AI 代替研发补造技术工作。

## 7. 一份文件、三张表

产品和研发共同面对一份《研发任务清单》，文件顶部显示：

- 清单编号、版本和当前状态；
- 本轮已经确认的交接范围；
- 公共需求、原型和研发评审材料；
- 产品确认与研发确认；
- 明确非范围、实施前置条件和阻断项；
- 版本变更摘要。

正文依次显示应用功能任务、外部系统接口任务和非页面研发任务三张表。产品经理不直接维护底层结构化数据，也不在多份表格中重复同步相同结论。

清单不包含任务负责人、排期、开发状态和完成比例。Jira、禅道或研发团队现有工具继续承担执行管理，避免形成第二套进度台账。

## 8. 材料入口与评审基线

“材料入口”表示研发或编程 AI 应到哪里查看这条任务对应的需求和原型，不要求复制完整文档，也不要求必须使用 Git。

可用入口包括：

- 钉钉文档链接或文档名称与章节；
- Git 文件路径、提交或标签；
- 原型网址、路由和具体菜单；
- 原型截图；
- 外部系统接口文档；
- 其他经确认且研发能够访问的位置。

所有任务共同使用的材料放在清单顶部；单条任务只标记相关章节、页面、接口或截图，避免表格过宽。

Kit 只要求材料可访问，并能够说明研发评审参考的是哪一版。能够自动获取版本或修改时间时记录并核对；暂时不能自动核对时显示“版本未自动核对”，允许研发人工确认。明确检测到评审后材料已经变化时，不得静默继续使用旧结论。

钉钉文档 CLI 可以作为材料读取方式，但核心模型不绑定具体 CLI、平台或凭证。访问凭证、令牌和真实敏感配置不得写入任务清单、提示词或业务材料。

## 9. 草稿、正式版和双确认

研发任务清单只使用三个文档状态：

- `draft`：AI 已形成拆分建议，等待研发评审或确认；
- `formal`：产品和研发完成双确认，可以作为开发范围基线；
- `superseded`：已有新版本替代，保留历史追溯但不再用于新实施。

首次从草稿转为正式版时：

- 产品经理确认需求覆盖、业务范围、非范围和验收结果；
- 研发负责人确认拆分、接口、研发端和非页面任务；
- 两方确认缺一不可；
- AI 只记录确认，不得代替任何一方。

未确认的业务范围、业务规则或验收结果会改变开发结果，对应任务不能进入正式版。接口联调时间、测试环境、数据准备等不会改变业务结果的事项，可以作为“实施前置条件”保留在正式版中。

## 10. 正式化前的四项覆盖检查

1. 需求覆盖：每条已确认需求至少关联一个任务，或明确标记“无需研发改动”；
2. 原型覆盖：本轮范围内已声明的应用端、菜单、页面和关键操作均能找到对应任务；
3. 接口覆盖：本轮触达的外部系统和接口均存在接口任务，或明确标记“本次不改”；
4. 任务反查：每个任务都能回溯到需求、研发评审结论或研发确认的技术必要项。

检查发现缺口时，清单保持草稿。AI 输出缺口和建议确认位置，不自动补造业务规则、接口或技术任务。

确定性检查只检查已声明 ID、引用、状态和映射；材料语义是否遗漏由 AI 辅助审查；研发任务是否技术完整最终由研发负责人确认。

## 11. 正式版后的变更规则

### 11.1 纯技术实现细节

不改变业务范围、任务边界和验收结果，例如内部代码重构，不更新正式任务清单。

### 11.2 原范围内的研发任务遗漏

例如研发发现遗漏幂等或定时任务，但业务范围和验收结果没有变化：

- 研发说明遗漏原因和依据；
- 新增任务并形成新版本；
- 研发负责人确认，产品经理知悉；
- 版本摘要明确标记“业务范围未变化”。

### 11.3 业务范围或验收变化

新增操作、状态、规则、接口能力或改变验收结果时，必须回到对应 CR 重新分析和确认，再形成新的正式任务清单版本。不得通过直接修改任务表绕过需求治理。

## 12. 单任务研发提示词

正式任务清单是所有研发都需要的交付物。单任务研发提示词只在研发使用 Codex、Cursor、Claude Code 等编程 AI 时按需生成。

研发选择一个任务编号后，AI 从正式任务清单及其关联材料生成：

1. 任务身份、清单版本和关联需求；
2. 任务目标；
3. 实施范围；
4. 禁止范围；
5. 已确认业务和研发评审依据；
6. 原型入口、页面和截图；
7. 验收标准及代表性异常；
8. 外部接口、数据和环境前置条件；
9. 不得自行补造规则、遇到冲突必须停止的执行约束；
10. 修改说明、检查结果、未完成项和遗留风险等交付要求。

研发提示词不提前批量生成，避免内容冗长和来源过期。提示词是临时生成视图，不反向成为需求或正式任务事实源。

以下两类动作必须分开：

- “为 `TASK-002` 生成研发提示词”：只输出提示词，不修改代码；
- “开始实施 `TASK-002`”：在现有授权和就绪门禁通过后，才允许执行该任务。

一次实施授权默认只覆盖明确指定的任务，不自动覆盖同一清单中的其他任务。

## 13. 与 V0.3 材料和状态的关系

- CR 和业务基线继续保存业务范围、规则和验收事实；
- 页面契约存在时提供页面、动作和状态依据，但轻量需求不会为了任务清单被强制创建页面契约；
- 正式研发任务清单是项目级、条件性材料，可以跨多条需求按应用端和外部系统聚合；
- 任务清单启用后，可以作为 `scope-clear`、依赖判断和实施授权的支撑证据，但不替代七项就绪检查；
- 任务清单不新增风险活动，不改变 `recorded → analysis-confirmation → implementation → awaiting-review → completed` 五阶段；
- 实施完成和需求完成仍然遵守 V0.3 的评审边界。

## 14. 产品经理与研发的自然语言交互

产品经理无需操作终端或 JSON，可以直接提出：

```text
根据当前已确认需求和原型，生成研发任务清单草稿。
```

研发评审结束后：

```text
根据这次研发评审记录更新任务清单，只列出新增、拆分、合并、删除和待确认差异。
```

完成双确认后：

```text
生成正式研发任务清单。
```

研发使用编程 AI 时：

```text
为 TASK-002 生成研发执行提示词，只生成提示词，不实施。
```

这些表达只触发对应动作，不自动推进下一步。
